> If you wish to update the documentation, **do not create a separate branch. Instead, commit directly to the branch corresponding to the version you're updating**.

# Platform documentation

This is the repository for the documentation of the platform. This *README* file contains information for those who wish to update the documentation. Users of the platform can find the documentation [here](https://scc-digitalhub.github.io/docs).

## Structure of repo branches

The repo's branches are structured as follows:

- Each branch named in a `x.y` format contains the documentation for the corresponding version of the platform.
- The `main` branch contains general files, notably the `config.env` one, which indicates the *stable* version of the platform.
- The `gh-pages` branch contains the actual website files.

## Create a new page

To create a new page (the following example refers to the `user` portal, but the process for others is equivalent):

- Write a *.md* file within `user/docs`
- Add it to the `nav` element in `/user/mkdocs.yml`

Commit your changes and the website will automatically be updated within a couple minutes.

## Test locally

If you wish to test your changes locally before pushing, the quickest way to do so is:

Install MkDocs and mkdocs-material:
```sh
pip install mkdocs
pip install mkdocs-material
```

Remove `custom_dir: ../custom/` from `base.yml` (this file concerns CSS, so things like colours will be different). If not removed, you may receive an error when performing the next step. Make sure not to include this change in your later commit.

Run the following from the `/user` (or equivalent for whichever portal you're testing) directory:
```sh
mkdocs serve
```

You can then view the docs at `localhost:8000`. As the docs on the website are generated by combining multiple portals, you will be missing any portal other than the one you are testing.

## Adding a portal

The documentation can feature multiple portals, such as `User` and `Admin`, aimed at different purposes, which can be accessed from a drop-down menu in the toolbar.

If you wish to add another portal, follow the steps below. This example will configure a new portal, called `Example`, available under the `/example` sub-path.

### 1. Directory structure for new portal

At root level, create a new directory named `example`. Inside, create a `mkdocs.yml` file, and a directory called `docs`, with an `index.md` file within, as follows:

```
example/
├── mkdocs.yml
└── docs/
    └── index.md
```

The contents of `mkdocs.yml` should be (replace `example` as needed):

``` yaml
INHERIT: ../base.yml
site_url: http://docs/example

extra:
  portal_name: Example
  portal_path: "/example"

extra_css:
  - !ENV [OTHERS_STYLESHEETS_PORTAL_SELECTION, "../stylesheets/portal_selection.css"]
  - !ENV [OTHERS_STYLESHEETS_COLORS, "../stylesheets/colors.css"]

nav:
  - "index.md"
```

Of course, you can add more *.md* files to expand your documentation, just make sure to list them under `nav`.

### 2. Update `base.yml`

Next, you must edit the `base.yml` file (found at the root), to expand the `extra.portals` list with your new portal. Note that `name` must be the same as `portal_name`, and `path` must be the same as `portal_path`.

``` yaml
extra:
  # [...]
  portals:
    - name: User
      path: ""
    - name: Admin
      path: "/admin"
    - name: Example    # Same as portal_name
      path: "/example" # Same as portal_path
```

### 3. Update workflow files

Finally, you must update the `.github/workflows/update-docs.yaml` workflow file, both on the **branch you're working on** and on the **main** branch. Make sure you do it in both.

You have to add two lines (duplicate the `admin` ones and adapt them to your new portal):

``` sh
# [...]
# First here...
git checkout $v
cd user && mkdocs build && cd .. && echo "Built user" || echo "No user portal"
cd admin && mkdocs build && cd .. && echo "Built admin" || echo "No admin portal"
cd example && mkdocs build && cd .. && echo "Built example" || echo "No example portal" # new line
# [...]
# and then a few lines later...
mkdir -p ./site
[ ! -d user/site ] || mv user/site site/$v
[ ! -d admin/site ] || mv admin/site site/$v/admin
[ ! -d example/site ] || mv example/site site/$v/example # new line
```

Remember to do this change on both branches as described above.

Once you commit these changes, your new portal will be available.

## How the website is generated

This section explains how the documentation website is generated, which may be useful for those wishing to update its features.

The documentation is built using [Material for MkDocs](https://squidfunk.github.io/mkdocs-material/), which enables generating a documentation website by writing only markdown and yaml files.

However, its base capabilities are limited. These features became essential to have:

- *Versioned documentation*: each version of the platform has its own docs.
- *Portals for different audiences or purposes*: separate docs for users, administrators, tutorials, etc.

These are to be selected via drop-down menus on the top toolbar, but otherwise must be independent: the navigation map on the left must only list articles within the current version and portal.

This is not supported by MkDocs. Hence, a number of workarounds were implemented.

A GitHub action orchestrates running `mkdocs build` to generate docs individually, for each version and each portal within, as if they're separate websites. Then, it organizes the generated docs properly in the directory structure of the `gh-pages` branch.

Each branch of the repository (named in a `x.y` format) is considered to be a separate version of the docs. Each portal needs its own name and must be listed in `base.yml`.

The drop-down menus that connect these docs are injected into the top-toolbar by customizing the `custom/main.html` file.

### Updates (workflow triggers)

- Pushing a commit to branch `x.y` will update the corresponding version's portal.
- Publishing a new `x.y` branch will generate its portal under `/docs/x.y`. It will also re-generate the docs of previous versions, to have the version drop-down menu include the new one.
- Pushing a change to the `main` branch's `config.env` file also re-generates docs of previous versions, to make the version drop-down menu update the *stable* annotation.

### Workflow files summary

- `generate-tutorials-metadata` - Generates a file needed by the platform to easily find metadata on tutorials present in the documentation. It does not do anything for the documentation itself.
- `update-docs` - Updates documentation as described in the sections above.
